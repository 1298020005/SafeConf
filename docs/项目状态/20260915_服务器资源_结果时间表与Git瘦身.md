## 4. Git 为什么显示约 901 MB

### 4.1 实测结果

| 对象 | 大小 |
| --- | ---: |
| 当前科研分支全部跟踪文件 | 91.71 MiB |
| 轻量 `master` 快照全部跟踪文件 | 71.71 MiB |
| GitHub 当前可达分支的压缩包估算 | 45.61 MiB |
| Gitee 当前可达分支的压缩包估算 | 63.36 MiB |
| 本地旧完整历史备份分支的压缩包估算 | 888.60 MiB |
| 本地 `.git` 目录 | 907 MiB |

旧历史最大的对象包括 20–51 MB 的预测数组、44 MB 的 bootstrap 明细，以及早期 27 MB 左右的长表。它们已经不在当前提交中，但本地 `backup/full-exp-20260820` 仍保留完整历史；Gitee 服务端也可能尚未回收旧对象，所以推送时仍按约 901 MB 提示。

### 4.2 当前仓库里哪些东西占空间

- 当前 Git 真正跟踪的内容约 92 MiB，没有跟踪 `node_modules`、Python 虚拟环境、`__pycache__` 或 checkpoint。
- 工作目录总计约 17 GiB，其中 `docs/实验结果` 约 9.3 GiB、`runtime` 约 6.0 GiB。这些大部分已被 `.gitignore` 排除，属于服务器本地实验资产，不会随新的 Git 提交上传。
- `runtime` 中约 5 GiB 是 2026 年 7 月的 SciPlex3 中间缓存；理论上可重算，但磁盘尚有 2.6 TiB，当前删除它们没有必要，也不能让远端仓库变小。
- 当前提交存在少量汇报图片副本，总共只节省约 1–2 MiB；贸然删除会破坏旧文档链接，对 901 MB 警告几乎没有帮助。

### 4.3 安全瘦身方案

分三步处理：

1. **现在**：继续使用当前科研分支保存协议、代码、小型表格和图；大型数组、模型、原始数据继续只放数据盘。E205/E208 期间不改写历史。
2. **给 Gemini 或外部代码审阅**：使用 `master`/`main` 轻量快照；进一步建立独立的 code-only 发布仓库，只保留 `code/`、必要 `tools/`、环境文件、测试和少量示例数据。该仓库应从干净快照新建，不能把 888 MB 旧历史一起推过去。
3. **E205/E208 封存完成后**：把 `backup/full-exp-20260820` 制作成离线 Git bundle，记录 SHA-256 后移到 `/home/yyf/archive/safeconf/`；再决定是否删除本地备份引用并执行垃圾回收。Gitee 若仍显示 901 MB，则申请服务端 GC，或把轻量快照迁移到新仓库。该步骤会改变克隆和历史使用方式，执行前必须留下恢复说明。

当前不执行 `filter-repo`、BFG 或强制推送。E205/E208 的盲态证据引用了具体提交哈希，直接重写会让已有记录失去可核对的提交链。
